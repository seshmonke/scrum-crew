# Инициализация проекта

Это **стадия 0**, а не спринт. Пока она не закрыта, спринт не начинается.
Цель — определить продукт и фундамент, а не написать код.

```
0.1 Product definition → 0.2 Technical foundation → 0.3 Delivery setup
→ 0.4 First change (walking skeleton) → Sprint 1
```

## 0.1. Определение продукта

Владелец отвечает, оркестратор записывает. Не выдумывать.

Вопросы (по одному, не списком):

1. Какую работу продукт делает для пользователя? Одна фраза.
2. Кто пользователь и какой у него болезненный момент?
3. Главный сценарий: вход → шаги → результат.
4. Как измерим успех? Число, время, конверсия, ошибки.
5. Что явно вне скоупа v1?
6. Ограничения: время, деньги, закон, данные, устройства.
7. Самое рискованное предположение. Как проверим дешево?
8. Что нельзя ломать: контракты, данные, безопасность, доступность.
9. Какой первый вертикальный срез докажет, что всё живо?
10. Есть ли требования к стеку или среде?

Выход:

```
docs/concept/product.md      Product Goal, пользователь, метрика, скоуп,
                             non-goals, ограничения, риски
docs/concept/personas.md    1–3 персоны, если нужны
docs/concept/journey.md     главный сценарий по шагам
```

Правила:
- Product Goal — одно предложение, наблюдаемый исход.
- Метрика — число и способ замера, не «стало удобнее».
- Non-goals явные; иначе скоуп расползётся.
- Гипотезы помечаются `hypothesis`, не выдаются за факты.
- Решение фиксируется до кода: дата, обоснование, trade-off.

**Гейт:** владелец подтвердил Product Goal, пользователя, главный сценарий,
метрику и non-goals. Без этого — стоп.

### 0.1.1. On-demand шляпы

На определении продукта решить, нужны ли:

- **Growth / Content** — запуск, лендинг, контент, SEO, кампании;
- **Support / Community** — реальные пользователи, тикеты, сообщество;
- **Legal / Privacy** — PII, cookies, платежи, регулируемые данные.

Это не постоянные роли. Отметить в `product.md`; активировать только под
соответствующий PBI. Legal имеет вето на релиз при нарушении закона или
приватности, но не заменяет юриста.

## 0.2. Технический фундамент

1. Стек: язык, фреймворк, БД, хостинг, auth, платежи.
2. ADR: контекст, решение, альтернативы, последствия.
3. `verify`: typecheck + lint + test + build + `openspec validate`.
4. CI: быстрый (< 5 мин), обязательные checks.
5. Preview-деплой на каждый PR.
6. Секреты — в хранилище, не в коде; у агентов нет прод-доступа.
7. Локальная среда: порты, БД, `.env.example`.

Выход:

```
docs/stack/adr/0001-stack.md
docs/stack/tooling.md
AGENTS.md (команды заполнены)
package.json / pyproject.toml / …
```

**Гейт:** `verify` запускается и падает осмысленно на пустом проекте;
preview открывается; секретов в репозитории нет.

## 0.3. Delivery setup

1. GitHub-репозиторий, `main` защищён.
2. Required checks: `verify`, `review-gate`, `security`.
3. 1 approval от не-автора; linear history; force push запрещён.
4. Merge train (для личного приватного репо — скрипт оркестратора).
5. `.scrum/` инициализирован: state, board, budget, events.
6. `openspec init --tools opencode --scope project`.

**Гейт:** нельзя запушить в `main` в обход PR; CI видит PR; `openspec
validate --all --strict` проходит.

## 0.4. Первый change: walking skeleton

Не «вся инфраструктура», не sprint 0, не «сначала авторизация».

Один вертикальный срез:

```
healthcheck → один экран → один API → одно чтение/запись БД → preview
```

- `openspec propose "walking skeleton: …"`.
- Один сценарий happy path + один error.
- Деплой на preview.
- Ревью не-автора.
- Archive после merge.

**Гейт:** preview живой, сценарий проходит, `verify` зелёный, change
заархивирован, владелец видел результат.

- [ ] `.scrum/` и `openspec/` инициализированы.

- [ ] Владелец дал команду на Sprint 1.

## Антипаттерны

- Начать со стека, не поняв продукт.
- Sprint 0 / «сначала вся инфраструктура».
- Product Goal «сделать удобно» без метрики.
- Скоуп без non-goals.
- Сразу все экраны и все роли.
- Писать код до утверждения сценария.
- Инициализация длится неделями: это часы, не спринт.
