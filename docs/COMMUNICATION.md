# Совместная работа агентов: шина, протоколы, ритм

Дополнение к `DESIGN.md`. Отвечает на требование: **субагенты работают
параллельно и взаимодействуют друг с другом внутри спринта.**

---

## 1. Принцип

Параллельность даёт **процессы**. Совместность даёт **шина сообщений и
общие артефакты**. Это не свободный групповой чат.

Формула:

> Параллельно работаем — через артефакты общаемся — решения фиксируем —
> конфликты разрешает названный решатель.

Свободный чат 12 агентов — худший вариант: квадратичный расход токенов,
сикофантия, циклы согласования, расхождение контекста. Поэтому общение
структурированное: типы сообщений, адресаты, дедлайны, доказательства.

### 1.1. Три уровня, а не один режим

Самый качественный вариант при неограниченной стоимости — не «всё в чате»
и не «только через оркестратора», а три уровня по типу работы:

| Уровень | Когда | Режим | Доля |
|---|---|---|---|
| **1. Шина + окна** | обычная работа, контракты, ревью | async JSONL + sync 10–15 мин | 80–90% |
| **2. Design council** | архитектурная/UX-развилка, спор о контракте | синхронные дебаты 3–5 ролей, 20 мин, модератор, decision | 5–15% |
| **3. Continuous** | P0, красный main, утечка, сломанный релиз | непрерывный канал, прерывает всё | < 5% |

Полный групповой чат на постоянной основе — **не самый качественный**:
он размывает ownership, повышает сикофантию и забивает контекст. Дебаты
дают качество только там, где действительно есть развилка и время
подумать. Поэтому — council точечно, а не как основной режим.

Правило: уровень 2 собирается только по триггеру (нет консенсуса за
2 раунда, цена ошибки высока, затрагивается контракт/деньги/PII/a11y).
Уровень 3 — только по инциденту. Всё остальное — уровень 1.

## 2. Техническая реальность OpenCode

Субагент OpenCode:
- запускается в дочерней сессии с чистым контекстом;
- работает в фоне, родитель получает отчёт по завершении;
- не имеет встроенной прямой связи «агент ↔ агент»;
- имеет свои права, модель и лимит шагов.

Отсюда три возможные схемы:

| Схема | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. Оркестратор-брокер** | родитель запускает субагентов волнами и передаёт сообщения | просто, безопасно, работает в v0.1 | нет настоящего real-time |
| **B. Почтовые ящики + именованные сессии** | у роли своя сессия `ses-fe`; оркестратор будит её при наличии письма | память между циклами, параллельные процессы | сложнее, нужен runner |
| **C. Свободный peer-to-peer** | MCP/A2A/локальный брокер | «как люди» | дорого, непредсказуемо, не нужно для одного продукта |

**Рекомендация:** v0.1 — A, v0.2 — B, C не делать без реальной
необходимости.

Ключевая мысль: агентам не нужен общий чат, им нужен **общий рабочий
стол**. Контракт, бриф, PR, ADR и доска — это и есть совместная работа.

## 3. Топология

```
                    ┌─────────────────────┐
                    │    Оркестратор      │
                    │  (SM + диспетчер)   │
                    │  маршрутизация,     │
                    │  дедлайны, бюджет   │
                    └──────────┬──────────┘
          ┌────────────────────┼────────────────────┐
          │                    │                    │
   ┌──────▼──────┐      ┌──────▼──────┐      ┌──────▼──────┐
   │ Product     │      │ Architect   │      │ Reviewers   │
   │ Owner       │      │ Tech Lead   │      │ QA/Sec/A11y │
   └──────┬──────┘      └──────┬──────┘      └──────┬──────┘
          │                    │                    │
   ┌──────▼────────────────────▼────────────────────▼──────┐
   │              Общая шина и артефакты                    │
   │  .scrum/bus/*.jsonl   contracts/   docs/   PR threads  │
   └──────▲────────────────────▲────────────────────▲──────┘
          │                    │                    │
   ┌──────┴──────┐      ┌──────┴──────┐      ┌──────┴──────┐
   │ Frontend    │      │ Backend     │      │ QA/Tester   │
   │ worktree 1  │      │ worktree 2  │      │ worktree 3  │
   └─────────────┘      └─────────────┘      └─────────────┘
```

Оркестратор — не «начальник», а **брокер и планировщик**: доставляет
сообщения, следит за дедлайнами, не даёт спорам разрастись, фиксирует
решения.

## 4. Шина сообщений

### 4.1. Каналы

| Канал | Назначение | Кто пишет | Приоритет |
|---|---|---|---|
| `#sprint` | цель, изменения плана, объявления | PO, SM | высокий |
| `#task-N` | рабочий поток задачи | owner + участники | обычный |
| `#contract` | контракты API/данных, breaking changes | Architect, BE, FE | высокий |
| `#review-N` | ревью PR | reviewers, author | обычный |
| `#incident` | красный main, CI, утечка, P0 | любой | прерывает всё |
| `#design` | UX-решения, состояния, токены | Designer, FE | обычный |
| `#spec` | дельта поведения, конфликт capability, spec freeze | PO, Architect, QA | высокий |

### 4.2. Схема сообщения

Одна строка JSONL в `.scrum/bus/<channel>.jsonl`:

```json
{
  "id": "msg-0042",
  "ts": "2026-11-26T10:14:00Z",
  "from": "frontend",
  "to": ["backend", "architect"],
  "channel": "task-42",
  "type": "question",
  "subject": "форма ошибки checkout",
  "body": "При пустой корзине API возвращает 200 или 409? Нужен точный контракт для UI.",
  "refs": {
    "task": "42",
    "pr": 118,
    "adr": "0007",
    "files": ["packages/contracts/src/checkout.ts"],
    "commit": "abc1234"
  },
  "correlation_id": "q-0017",
  "requires_response_by": "2026-11-26T10:29:00Z",
  "confidence": "high",
  "evidence": ["curl ... -> 200 {\"items\":[]}"]
}
```

Правила:
- тело ≤ 1200 символов; одна тема — одно сообщение;
- вопрос обязан иметь `requires_response_by` и `correlation_id`;
- `ack`-сообщения запрещены; подтверждение = ответ по существу;
- решение обязано ссылаться на артефакт (ADR, контракт, PR, коммит);
- всё, что старше TTL (2 цикла), помечается `stale` и перепроверяется.

### 4.3. Типы сообщений

| Тип | Смысл | Обязательный ответ |
|---|---|---|
| `question` | нужен факт/решение | да, до дедлайна |
| `answer` | ответ на question | нет |
| `proposal` | предлагаю решение | возражения до дедлайна |
| `objection` | возражаю, с доказательством | да, автору |
| `decision` | решение принято, решатель назван | нет |
| `handoff` | передаю задачу/контекст | подтверждение получателя |
| `blocker` | не могу двигаться | немедленно |
| `review` | находки ревью | да, по каждой |
| `status` | 1 строка для дейлика | нет |

## 5. Протоколы взаимодействия

### 5.1. Вопрос → ответ (максимум 2 раунда)

1. Автор задаёт вопрос с дедлайном (по умолчанию 15 минут внутри цикла).
2. Адресат отвечает фактом или ссылкой на артефакт.
3. Не ответил — оркестратор назначает другого или эскалирует.
4. Два раунда не дали ответа — решает названный решатель, вопрос
   фиксируется как риск. Дальше не спорим.

### 5.2. Предложение → возражение → решение (consent, не consensus)

1. Owner публикует `proposal` с trade-off и дедлайном (10 минут).
2. Затронутые роли могут дать `objection` только с доказательством:
   тест, контракт, замер, стандарт.
3. Нет возражений до дедлайна — предложение принято.
4. Возражение есть — решает названный решатель:
   - ценность/приоритет — PO;
   - архитектура/контракт — Architect;
   - процесс — SM;
   - безопасность — DevSecOps/White Hacker (вето только на security-риск);
   - UX — Designer (вето только на a11y/разрушение сценария).
5. Решение пишется в `decision` и в соответствующий артефакт.

Это защита от «согласования всего со всеми». Consent: не «все за», а «нет
обоснованных возражений».

### 5.3. Передача задачи (handoff)

Owner пишет `handoff.md`:
- что сделано и где (файлы, коммит, PR);
- что осталось и следующий шаг;
- грабли и неочевидное;
- какие проверки запускались и их результат;
- какие сообщения/треды ещё открыты.

Получатель отвечает **read-back**: одной строкой пересказывает, что
понял, и что делает дальше. Без read-back задача не считается переданной.

### 5.4. Ревью

- Ревьюер — не автор, желательно другая модель/провайдер.
- Находка: severity `P0–P3`, файл:строка, доказательство, предлагаемое
  действие.
- Автор отвечает по каждой находке: исправлено / отклонено с причиной /
  вопрос.
- Стиль и форматирование — линтеру, не ревьюеру.
- Максимум 3 блокирующих находки на PR; остальное — задачи в бэклог.

### 5.5. Блокер

`blocker` прерывает focus-window и идёт в `#incident`/`#task-N`.
Оркестратор в течение одного цикла:
1. переназначает задачу;
2. или меняет план;
3. или эскалирует PO/владельцу.
Задача не «висит» молча.

### 5.6. Парная работа

Для рискованных задач:
- **driver** пишет код и коммитит;
- **navigator** читает, задаёт вопросы, пишет в `thread.md`;
- у обоих один worktree, но право записи в код — только у driver;
- спор решает Architect/PO, а не «кто громче».

### 5.7. Ревью-сворм

На один PR параллельно:
- QA — тестируемость и покрытие;
- DevSecOps — authz, секреты, зависимости;
- Designer/a11y — доступность и состояния;
- White Hacker — abuse cases.

Оркестратор дедуплицирует находки и отдаёт автору один список. Это
параллельность, которая реально повышает качество, а не плодит ветки.

### 5.8. Изменение поведения (OpenSpec)

Спека — такой же контракт, как API. Поэтому:

1. Автор изменения публикует в `#spec` ссылку на change и diff:
   `openspec show <change> --diff`.
2. PO проверяет «зачем» и скоуп, Architect — границы capability,
   QA — наблюдаемость сценариев.
3. Возражение — только со ссылкой на существующую спеку, тест или
   стандарт.
4. После `decision` — **spec freeze** до конца apply. Менять спеку на
   ходу можно только новым циклом review.
5. `openspec/specs/` не правится в ветке фичи. Только archive после merge.
6. Два change на одну capability в одной волне запрещены: либо
   последовательно, либо дробить capability.

Архитектурная развилка по спеке → уровень 2 (design council), 20 минут,
решатель — Architect. Конфликт ценности → PO. Конфликт процесса → SM.

## 6. Ритм: два окна внутри цикла

Цикл 60–90 минут делится на:

| Окно | Длительность | Что можно |
|---|---|---|
| **Sync** | 10–15 мин | вопросы, ответы, контракты, планирование, дейлик |
| **Focus** | 45–60 мин | только `blocker`, `decision`, `incident`; остальное в очередь |

Почему так: постоянные пинги убивают работу. Совместность нужна в точках
стыковки, а не каждые 30 секунд.

Дейлик стоит на границе цикла и открывает sync-окно.

## 7. Пример: checkout за один цикл

**t+0, planning/sync**
- PO: цель — гость может оформить заказ.
- Architect: публикует контракт `POST /checkout` и схему ошибок.
- FE и BE задают 2 вопроса, получают ответы, возражений нет — контракт
  принят (`decision`).

**t+15, focus**
- BE: реализует endpoint в worktree 2.
- FE: собирает форму в worktree 1 по контракту.
- QA: пишет e2e против контракта, не против реализации.
- Designer: проверяет пустое/ошибочное/загрузочное состояние.
- DevSecOps: добавляет authz-тест и rate limit.
- White Hacker: проверяет abuse case «чужой cart id».

**t+40, sync**
- FE: «API вернул 409 без тела — это ожидаемо?»
- BE: отвечает ссылкой на схему, Architect подтверждает.
- QA: находит, что e2e не покрывает повторную отправку.
- Решение: добавить idempotency key, задача в тот же цикл.

**t+55, merge train**
- BE PR → review swarm → merge.
- FE rebase → e2e → review → merge.
- QA PR с тестами → merge.
- main зелёный, preview обновлён.

**t+75, daily**
- 3 строки от каждого активного, 2 блокера, план на следующий цикл.

Это и есть параллельно + совместно: разные worktrees, общий контракт,
короткие структурированные сообщения, последовательный мерж.

## 8. Оркестратор-брокер

Обязанности:
1. Доставлять сообщения по `to`/каналу.
2. Следить за `requires_response_by`; просрочка → напоминание → эскалация.
3. Ограничивать раунды (2) и бюджет сообщений на задачу.
4. Сводить duplicate findings.
5. Фиксировать `decision` в артефакте, а не только в чате.
6. Не давать двум агентам править один файл: lease.
7. Останавливать «переписку ради переписки».

Права:
- снять агента с задачи;
- назначить другого решателя;
- заморозить тред;
- эскалировать владельцу.

## 9. Защита от хаоса

| Риск | Лимит / правило |
|---|---|
| Бесконечный диалог | максимум 2 раунда, потом решает названный решатель |
| Квадратичный рост токенов | бюджет сообщений: ≤ 6 на задачу за цикл |
| «Все согласны» без проверки | consent + доказательство для возражения |
| Два агента правят файл | lease на файл/директорию + file scope в брифе |
| Рассинхрон контрактов | contract-first, `#contract`, ADR |
| Потеря сообщения | append-only JSONL + ack по существу + TTL |
| Агент игнорирует почту | оркестратор будит сессию; нет ответа — эскалация |
| Статус-отчёты вместо работы | `status` только 1 строкой в дейли |
| Свободный чат | запрещён; только типизированные сообщения |

## 10. Реализация

### v0.1 — оркестратор-брокер (без кода)

- Шина — JSONL-файлы в `.scrum/bus/`.
- Оркестратор запускает волну субагентов, собирает отчёты, маршрутизирует
  сообщения, запускает следующую волну.
- Каждый субагент получает в промпте:
  - прочитать входящие сообщения по своей задаче;
  - ответить в outbox по схеме;
  - не писать `ack`;
  - соблюдать дедлайн.
- Параллельность: несколько субагентов в фоне; WIP ≤ 4.

### v0.2 — именованные сессии и почтовые ящики

- У каждой роли своя сессия: `ses-po`, `ses-fe`, `ses-be`, ...
- `.scrum/bus/inbox/<role>.jsonl`, `outbox/<role>.jsonl`.
- Runner: `opencode run --session ses-fe "прочитай inbox, ответь, работай"`.
- Оркестратор запускает несколько процессов параллельно, каждый в своём
  worktree.
- Память роли сохраняется между циклами: агент помнит свою задачу.
- Скрипты: `bus.ps1`, `dispatch.ps1`, `standup.ps1`, `merge.ps1`.

### 10.1. Именованные сессии: память + гигиена

Память роли не должна превращаться в свалку. Правило:

- Сессия роли хранит **устойчивое**: конвенции, принятые решения, свои
  артефакты, открытые треды.
- На старте apply агент читает **только** change-папку, контракты и
  релевантные доки, а не всю историю сессии.
- На archive агент пишет 5 строк в `memory/<role>.md`: что решил, что
  выяснил, где грабли. Остальное — в change/ADR, не в голове.
- Смена change = смена working set. Контекст чистится, память остаётся.
- OpenSpec сам рекомендует чистый контекст для apply; поэтому apply
  запускается отдельной сессией на change, а не в сессии PO.

Так сохраняется и «помнит между циклами», и «не тащит мусор».

### v0.3 — при необходимости

- SQLite/HTTP-брокер или MCP-сервер для сообщений.
- A2A — если появятся агенты вне OpenCode.
- Не раньше, чем v0.2 упрётся в реальные ограничения.

## 11. Метрики совместной работы

- Время ответа на вопрос (медиана, p90).
- Доля вопросов, закрытых за 1 раунд.
- Число эскалаций на цикл.
- Конфликты мержа на 100 PR.
- Дублирующиеся находки ревью (эффективность дедупликации).
- Токены на коммуникацию / общие токены (цель ≤ 15%).
- «Тишина после дедлайна» — сколько решений принято без ответа.
- Rework после ревью.

## 12. Антипаттерны

- Групповой чат «все со всеми» без адресата и дедлайна.
- 12 агентов по очереди рассказывают статус.
- Согласование решения, которое уже принято.
- Обсуждение в чате без фиксации в артефакте.
- Ревьюер, который правит код вместо автора.
- Два агента в одном worktree без правила «кто коммитит».
- Параллельный мерж нескольких PR.
- Бесконечные «уточняющие» вопросы вместо чтения контракта.
- Агент, который молча ждёт ответа вместо `blocker`.
