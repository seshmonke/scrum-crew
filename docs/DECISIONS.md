# Журнал решений методологии

Формат: решение → почему → последствия → статус.
Дата: 2026-11-26.

---

## D1. Одна команда, один бэклог, один монорепозиторий

**Статус:** принято.
**Почему:** Scrum требует одну кросс-функциональную команду на продукт.
Репозиторий на роль — компонентные команды, очередь интеграции и рассинхрон
контрактов.
**Последствия:** изоляция через worktree и короткоживущие ветки, а не через
отдельные репозитории.

---

## D2. 12+ permanent-мест, 12 слотов в коде

**Статус:** принято.
**Почему:** владелец хочет все роли постоянно и максимальную
параллельность; стоимость не является ограничением.
**Последствия:** 12 слотов staffed постоянными ролями-владельцами зон +
worker-субагентами на задачу (постоянных coding-ролей меньше 12). Нужны
contract baseline, file ownership, shared-file czar, contract sentinel,
batch merge и circuit breaker. Без них 12 параллельных веток дают merge
hell.
**Предохранитель:** при конфликтности > 15%, красном main > 30 мин или
очереди ревью > 8 PR — WIP снижается до 6 до конца цикла.

---

## D3. Спринт = 4–6 циклов по 60–90 минут

**Статус:** принято.
**Почему:** сессия 4–8 часов; дейлик должен стоять на границе
инкремента, а не на таймере.
**Последствия:** 4–6 дейликов за спринт, каждый ≤ 10 минут; церемонии
≤ 20–25% бюджета.

---

## D4. Полный автопилот + аварийный контур человека

**Статус:** принято.
**Почему:** владелец хочет автономный спринт.
**Последствия:** человек нужен только на: концептуальное решение, прод-релиз
и прод-секреты, инцидент безопасности, бюджет > 90%. Всё остальное решают
агенты по домену.

---

## D5. Контракты-first + worktrees + merge train

**Статус:** принято.
**Почему:** личный приватный репозиторий не даёт GitHub merge queue;
параллельный мерж ломает main.
**Последствия:** последовательный squash-merge, rebase перед мержем,
повторный `verify`, один мерж за раз.

---

## D6. Скилл + `.scrum/`, v0.1 без кода

**Статус:** принято.
**Почему:** методологию нужно проверить за дни, а не недели; код нужен
только для состояния, локов, бюджета и merge train.
**Последствия:** v0.1 — markdown-скилл; v0.2 — тонкие скрипты; v1 —
сервис только при необходимости.

---

## D7. Документация по стандарту солоспринт-конвеера

**Статус:** принято.
**Почему:** владелец уже использует этот диалект.
**Последствия:** `docs/concept`, `docs/stack`, `docs/design`,
`docs/quality`, `docs/tasks`; один факт — один файл; чистовик; milestones;
файл спринта `NN-*.md`.

---

## D8. OpenSpec — слой поведения

**Статус:** принято.
**Почему:** нужен ревью намерения до кода, сценарии вместо размытых AC,
постоянный контекст и brownfield-подход.
**Последствия:**
- behavior-changing PBI = `openspec/changes/<id>/`;
- DoR: `validate --strict`; DoD: `verify-change` + archive;
- `openspec/specs/` — чистовик поведения, `docs/` — причины и реализация;
- архив после merge, отдельным PR в конце цикла;
- spec-worthy threshold, чтобы не гонять опечатки через change.

---

## D9. Именованные сессии с памятью между циклами

**Статус:** принято.
**Почему:** агент не должен каждый цикл перечитывать всё заново.
**Последствия:** у роли своя сессия (`ses-po`, `ses-fe`, ...), но apply
идёт в отдельной сессии на change; на archive — 5 строк в
`memory/<role>.md`, остальное в артефакты.

---

## D10. Решатель по домену

**Статус:** принято.
**Почему:** голосование медленно и уязвимо к сикофантии; один PO — узкое
место в технике.
**Последствия:** PO — ценность, Architect — контракт/архитектура, SM —
процесс, security — вето на риск, Designer — вето на a11y/сценарий.

---

## D11. Трёхуровневая связь

**Статус:** принято.
**Почему:** максимальное качество/скорость даёт не свободный чат, а
структурированная шина + точечные дебаты + continuous только для
инцидентов.
**Последствия:**
1. шина + sync/focus — 80–90% работы;
2. design council 3–5 ролей на 20 мин — только на развилках;
3. continuous — только P0/красный main/утечка.

---

## D12. Определение продукта — стадия 0

**Статус:** принято.
**Почему:** без Goal, пользователя, сценария, метрики и non-goals любой
спринт — гадание, а не Scrum.
**Последствия:** Init (продукт → стек → delivery → walking skeleton)
закрывается до Sprint 1. Код до закрытия Init не пишем. Init — часы, не
недели и не «sprint 0».

---

## D13. Скилл опубликован отдельным публичным репозиторием

**Статус:** принято.
**Почему:** методология должна переиспользоваться в новых проектах, а не
жить в одном репозитории.
**Последствия:** скилл и агенты лежат в
[seshmonke/sprint-crew](https://github.com/seshmonke/sprint-crew);
установка — `install.cmd` / `install.ps1` / `install.sh`; каркас проекта —
в `template/`. Версия v0.1.0.

---

## D14. Methodology Auditor — on-demand, только при материалах

**Статус:** принято.
**Почему:** ретро видит один спринт; нужен кросс-спринтовый анализ
методологии, стоимости и поведения агентов.
**Последствия:** отдельная read-only роль; запуск после 3-го спринта или
по команде; pilot — 1 спринт / 5 merged, full — 3 спринта / 20 merged;
1–3 находки, owner, метрика; изменения через ADR/PR; нет эффекта два
аудита — роль удаляется.

---

## Решено при сборке v0.1

1. **Archive timing.** После merge, отдельным PR в конце цикла.
2. **Spec-worthy threshold.** Принят список исключений: багфикс,
   рефакторинг без поведения, инфра/CI/доки, косметика.
3. **OpenSpec install.** Установлен 2.2.0 (standalone), инициализирован
   `--tools opencode --scope project`; версия в `docs/stack/tooling.md`.
4. **12 слотов.** Принят circuit breaker: 15% конфликтов / 30 мин
   красного main / 8 PR в ревью → WIP 6 до конца цикла.
